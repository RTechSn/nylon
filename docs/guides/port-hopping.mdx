Port hopping makes a nylon tunnel survive middleboxes that block UDP traffic by flow volume rather than by port alone. Typical behaviour (empirically observed on networks with TSPU-style DPI):

- every UDP **flow** — a 5-tuple of src ip:port and dst ip:port — is permanently banned after a small number of packets (on the order of 16–20, roughly 20–24 KB at a 1200-byte safe MTU);
- individual ports are periodically banned outright, but the bans are much slower and recover after minutes.

A tunnel pinned to a single `ip:port` cannot survive the first behaviour at all: the flow is banned after seconds of traffic. Port hopping answers it by treating the destination port as a consumable resource: traffic rides one port until its packet budget is nearly spent, then rotates, without interrupting the WireGuard session.

## Design in one paragraph

Nylon already supports multiple endpoints per peer with probe-based ranking. Port hopping reuses that machinery: a peer configured with a **port range** (`203.0.113.7:30000-40000`) is *not* expanded into thousands of links at startup. Instead a **port factory** keeps exactly one *carrying endpoint* alive at a time, draws new ports from a **port pool** as the old ones burn out, and materialises each drawn port as a regular nylon link that the existing probe/metric/ranking code can see. Runtime state is O(active window), not O(range), which is what makes production-sized ranges (tens of thousands of ports) viable.

The rotation itself lives in the device send path (a per-peer packet budget enforced on every outgoing batch — data, retransmits, keepalives, probe packets and AmneziaWG junk all count), so the switch to a fresh port is immediate and never waits for the nylon control loop. The WireGuard session is port-agnostic (transport data is decrypted by receiver index), so rotation needs no new handshake and nothing is injected into the encrypted stream — AmneziaWG compatibility is preserved by construction.

## Server side

The server must accept packets on **every** port of its advertised range and — crucially — answer each peer from exactly the port that peer's last packet targeted. There are two modes; both satisfy the same contract, so the client cannot tell them apart:

### In-daemon range listener (default, up to 4096 ports)

Set `listen_ports` in the server's `node.yaml` (the default `listen_mode: sockets`). The daemon binds one extra UDP socket per port and tags received packets with the receiving port, so replies leave through the same socket (NAT path symmetry):

```yaml title="node.yaml (server)"
port: 57175
listen_ports: 57175-57575 # must contain the primary port; max 4096 ports wide
listen_mode: sockets # default, may be omitted
```

This mode is the simplest and works everywhere without root firewall changes, but every port costs file descriptors and one receive goroutine per address family, hence the ceiling. Budget roughly `0.6 MB` of resident memory per range port (receive buffers plus socket overhead): a 500-port range sits around 300 MB above the daemon baseline, and the full 4096-port ceiling around 2.5 GB. Plan file descriptors accordingly — the range needs about `2 × ports` descriptors (IPv4+IPv6) plus headroom; `LimitNOFILE=8192` (as shipped in `nylon.service`) covers ranges up to a few thousand ports. A bind failure is fatal at startup by design — the daemon refuses to run with a half-open range — so a *running* daemon either has the full range or none of it.

### Netfilter DNAT mode (daemon-managed, arbitrarily wide ranges)

For wide ranges, `listen_mode: nftables` keeps the daemon on its single primary-port socket and lets the kernel do the range: at startup the daemon installs (and at shutdown removes) an nftables table that redirects the whole listen range to the primary port, and conntrack mirrors the reverse direction:

```yaml title="node.yaml (server)"
port: 57175
listen_ports: 1024-65535 # must contain the primary port; no width ceiling in this mode
listen_mode: nftables
```

The daemon owns the `inet nylon` nftables table while running; the ruleset it maintains is equivalent to:

```bash title="nftables (what the daemon installs)"
table inet nylon {
  chain prerouting {
    type nat hook prerouting priority dstnat; policy accept;
    udp dport 1024-65535 redirect to :57175
  }
}
```

With the redirect in place, the kernel rewrites inbound packets destined to any port of the range to the real listen port, and conntrack automatically rewrites the *source* of the replies back to the original destination port — the program never needs to know which port the peer targeted. The server only binds its normal `port: 57175`, so sockets, file descriptors and receive memory stay **O(1)** regardless of range width: a 500-port range costs the same as no range at all, and tens of thousands of ports are fine. Because all traffic rides the primary socket, the range-listener throughput and memory ceilings of the sockets mode (capped receive batches, no GRO/GSO offload on extra sockets) do not apply — the data path performs like a plain single-port node.

Requirements and behaviour:

- Linux only, and the daemon needs `CAP_NET_ADMIN` (run as root, or grant the capability to the binary). A failure to install is **fatal at startup** by design — the daemon refuses to run with a half-served range, same contract as a failed socket bind in the sockets mode.
- `conntrack` keeps state for each flow; idle UDP flows time out from the conntrack table, which is harmless — the next packet from the peer creates a new mapping.
- Install is idempotent: a table left behind by a crash (or a concurrent instance) is replaced wholesale on the next start. On graceful shutdown the table is removed; after a crash it lingers harmlessly (it only redirects to a port nothing listens on) and is reclaimed on the next start. Only one nylon daemon per host may own the table.
- Pick ranges that do not overlap other services on the host, and make sure the firewall allows the whole UDP range — a rule for the primary port alone is not enough (the redirect happens in `prerouting`, before any filter policy you may add).
- Hub-initiated traffic to a peer (probes before the peer ever contacts us) leaves from the primary port; it is still attributed correctly by range-aware peers, and reply traffic to an active peer rides that peer's own conntrack mapping, i.e. rotates in lockstep with the peer's hops.

If you prefer to manage the firewall yourself, the mode also works with hand-written rules: omit `listen_mode` (or set `sockets` but *not* `listen_ports`), bind only `port: 57175` and install the table above manually — the daemon then simply never learns about the range, and `nylon verify` cannot check it for you.

## Client side

Two config entries enable hopping on the client:

1. The server's entry in `central.yaml` advertises a **range endpoint**:

```yaml title="central.yaml (excerpt)"
routers:
  - id: server
    # ...
    endpoints:
      - "203.0.113.7:30000-40000"   # port range: any port in [30000, 40000]
      # additional concrete endpoints (e.g. a LAN IP) may be listed and are
      # used by the stock failover machinery as usual
```

2. The client opts in with an explicit `port_mode` (and its policy knobs):

```yaml title="node.yaml (client)"
port_mode: proactive    # static | reactive | proactive | timed
port_hopping:
  budget_packets: 12   # proactive: rotate the carrying port after N wire packets (default 12)
  period_seconds: 300  # timed: rotate every N seconds (required in timed mode)
  period_jitter_pct: 10 # timed: random jitter around the period, % of it (default 10, max 50)
  recent_ports: 512    # never redraw the last N selected ports (default 512)
  cooldown_seconds: 180 # quarantine a retired port for this long (default 180)
  candidate_samples: 32 # candidates scored per draw for diversity (default 32)
```

### Rotation modes

`port_mode` decides **when** the carrying endpoint of a range-configured peer changes. It governs the node's outgoing connections only — the listen half (`listen_ports`/`listen_mode`) is orthogonal, so a hub may serve a wide range while itself running any mode.

| Mode | Rotates | Required knobs | When to use |
| --- | --- | --- | --- |
| `static` (default) | never — pinned to the first port of the first range | — | no hopping protection; compatibility and lowest churn |
| `reactive` | only when the carrying link is dead or our probes go unanswered | — | minimal port churn; tolerates occasional flow bans with a short blackout |
| `proactive` | after `budget_packets` wire packets on the carrying port | `budget_packets` | worst-case per-flow volume: every flow stays under the middlebox's ban threshold (the TSPU countermeasure) |
| `timed` | every `period_seconds` ± jitter | `period_seconds` | fixed cadence independent of traffic volume |

`dynamic` (proactive with an automatically sized budget) and `auto` (automatic mode switching) are reserved names: the parser accepts them, validation rejects them with a not-implemented error until their branches land.

The policy can also live in `central.yaml` on the router entry — and when it does, it wins **wholesale** over `node.yaml`:

```yaml title="central.yaml (excerpt, router entry)"
routers:
  - id: client-node
    port_mode: proactive
    port_hopping:
      budget_packets: 12
      cooldown_seconds: 180
```

Precedence: the central router entry (when it sets `port_mode` or `port_hopping`) overrides the node's `node.yaml` hop fields entirely; otherwise `node.yaml` applies; otherwise the `static` default. The active policy is journaled on every change: `port hop policy applied mode=proactive source=central budget=12`.

::::caution
**Migration from pre-`port_mode` builds:** earlier builds rotated by packet budget implicitly whenever `port_hopping` was set. This build refuses to guess: a `port_hopping` block without a `port_mode` (in the same file) fails validation with an explanation. Add `port_mode: proactive` to keep the previous behaviour.
::::

Notes per mode:

- **static** — the carrying endpoint is the first port of the first resolvable range spec; knobs the mode does not use (e.g. a leftover `budget_packets`) are ignored. A config change of the range re-pins automatically (`port hop: static pin moved, re-pinning`).
- **reactive** — rotation fires when the carrying link is judged dead by the same liveness model the router uses for ranking (no traffic heard back for `link_dead_threshold`, or loss-dead probe statistics), **or** when three consecutive probes of the carrying port go unanswered. The second trigger matters: the peer's own traffic can keep a link "alive" while *your* direction to the port is blackholed — only your probes going unanswered exposes that asymmetry. Expect a rotation (with `reason=...` in the journal) one to two probe cycles after a ban.
- **proactive** — unchanged behaviour; see the tuning notes below and [Behaviour under load](#behaviour-under-load).
- **timed** — the rotation deadline is checked on the one-second reconciliation pass, so effective intervals are the period plus up to a second; each interval is drawn as `period ± period*period_jitter_pct/100` so rotations never synchronise. A rotation that fails (port pool fully cooling down) stays due and retries on the next pass.

### Tuning notes

- `budget_packets` (proactive) must stay **below** the middlebox's per-flow budget. The default 12 leaves headroom under the worst observed 16–20 for handshake junk and in-flight packets at rotation time. Overshooting a few packets is harmless in practice: the port is retired immediately after, and a ban on an abandoned port costs nothing.
- `period_seconds` (timed) should be short enough that a flow never accumulates ban-worthy volume between rotations, and long enough not to churn NAT state or flood the cooldown pool. With the default 3-minute cooldown, periods down to ~10 s are safe for ranges of a few hundred ports.
- `cooldown_seconds` should be at least the observed middlebox recovery time. Range longevity is bounded by `sustained ≈ (ports / cooldown) × budget × ~1200 B`: 40 000 ports with a 180 s cooldown sustain roughly 35 Mbit/s indefinitely; a 100-port test range with the default policy sustains idle probing comfortably (a few ports per minute) but not heavy traffic. When the pool does run dry, rotation stalls (traffic keeps flowing on the burned port) and nylon warns at most once a minute with the pool stats — `port hop: rotation stalled, port pool exhausted ... cooling=N`.
- The carrying link is probed at a relaxed cadence (a fraction of `link_dead_threshold`) so idle probing does not burn the budget; active traffic rotates the port naturally. A link that is not yet (or no longer) active is always probed at the stock cadence — recovery is never gated.

### Behaviour under load

Rotation rate follows the traffic: one rotation per `budget_packets` wire packets, so a saturated link rotates its port hundreds of times per second (at iperf3 speeds with the default budget). This is by design — it is the only way a single flow stays under the per-flow volume ban — and the control plane absorbs it cheaply:

- the rotation hot path does no dispatch work; link bookkeeping is reconciled once per second, so a rotation storm costs one materialisation per second, not one per rotation,
- ports drawn and abandoned between two reconciliation passes never become links (nothing probed them, so nothing needs to match them),
- the freshly drawn port's link is seeded with the predecessor's RTT estimate, so routes stay feasible and their cost continuous across every rotation — the neighbour never flaps to `no endpoint to neighbour` because of rotation,
- `port hop: carrying endpoint rotated` is logged at most once per second at INFO with a `rotations=N` counter covering the interval (every individual rotation is DEBUG).

## Multi-IP diversity

Range endpoints may list **different IPs** (the natural Stage-2 extension):

```yaml
endpoints:
  - "203.0.113.7:30000-40000"
  - "198.51.100.9:30000-40000"
```

When drawing a new carrying port, the pool scores candidates by dissimilarity to the currently active window and prefers, in order: a **different IP subnet** → a **different IP in the same subnet** → the same IP on a different port. Ties break randomly, so port usage stays unpredictable. If TSPU ever bans one path or prefix wholesale, the next rotation moves the tunnel to another address family of your endpoint set.

## Observability

Every policy change is journaled with its winning source:

```
INFO port hop policy applied mode=proactive source=central budget=12
INFO port hop policy applied mode=timed source=node period=5m0s jitter_pct=10
```

Per-rotation logs (`port hop: carrying endpoint rotated`, with peer and endpoint) land at INFO — at most one line per second under load, carrying a `rotations=N` counter of the rotations it covers, and a `reason` attribute on externally driven rotations (`reason="timed schedule"`, `reason="dead carrying link"`, `reason="unanswered carrying probes"`). Static mode logs its pin once (`port hop: static carrying endpoint pinned`). The device UAPI (`wg show nylon dump`) reports per-peer:

```
hop_budget=12
hop_endpoint=203.0.113.7:30142
hop_budget_left=7
```

`hop_budget=0` means the carrying endpoint rotates externally (static/reactive/timed) rather than by packet budget. The rotation counters in the logs are the quickest way to verify proactive hopping is active: under sustained load expect one INFO line per second with a large `rotations=N`; while idle, a new endpoint line every ~minute as the relaxed probes burn the budget. In timed mode expect one rotation line per period; in reactive mode one line per detected death.

### Verifying the server side

On the server, the startup log confirms which server-half mode is active:

```
INFO port hopping range listener active listen_ports=57175-57575 ports=401 primary_port=57175
INFO port hopping nftables redirect active listen_ports=1024-65535 ports=64512 primary_port=57175 table=inet nylon
```

Sockets mode — two checks are definitive:

```bash
# 1. the UAPI dump carries the range (absent => old binary or missing listen_ports)
wg show nylon dump | grep listen_ports
#    listen_ports=57175-57575

# 2. the sockets exist (UDP has no LISTEN state — netstat -aon | grep LISTEN
#    shows only TCP/unix and never lists a UDP range)
ss -ulnp | grep -c 57175 # ~2 per port: one v4 + one v6 line
```

Nftables mode — the daemon-owned table is the state:

```bash
nft list table inet nylon # the redirect rule must cover the whole range
```

A hopping client that logs endless `carrying endpoint rotated` lines while the tunnel passes no traffic is rotating through dead ports: on the server, confirm the startup log for the active mode, the sockets / `nft list table inet nylon` state, then check the firewall (`nft list ruleset`, `ufw status`) allows the whole UDP range — a rule for the primary port alone is not enough.

## Threat model and limits

- **Per-flow volume bans** are neutralised as long as the range is large enough for the cooldown arithmetic above.
- **Per-port bans** are sidestepped for the same reason: each port is used only briefly and then rests for the cooldown.
- **Full IP/prefix bans** are out of scope for a single-address range; use multi-IP endpoints for path diversity.
- The reverse direction (server → client) rides the same ports (the server replies from the port the client targeted), so its budget burns in lockstep with the client's rotations — no separate server-side rotation is needed.
- Vanilla WireGuard peers and non-hopping nylon peers are unaffected: no protocol bytes changed, and nodes without range endpoints behave exactly as before.
